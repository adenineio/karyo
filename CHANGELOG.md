# Changelog

The `karyo` Claude Code plugin (`.claude-plugin/plugin.json`). Newest first.

## Unreleased

## 0.3.0

- **A demo ships with the plugin:** `/karyo:demo` (or `karyo demo claude-code`) builds "Claude Code, explained", 21 explainers and a map of them, to HTML pages in the plugin's data dir and opens the map in the browser; later runs reuse the build until Karyo or the demo changes. `karyo demo` lists the demos (`demos/<name>/demo.json`); `--no-open`, `--out DIR` and `--force` as you'd expect.
- **Explainers:** an optional top-level `note` (markdown-lite inline) is shown in the footer on every step, in stills, lint and built files, e.g. "Names and files here are made-up examples."; the `code` component tints shell (`lang`: sh, bash, zsh, just, make: `#` comments, quotes, `$VAR` / `{{var}}`, reserved words) and has `text` for no tint; only props a component declares as images (`"format": "image"`, as `image` and `figure` mark `src`) are inlined when bundling, so a file name such as `IMG_2207.png` in text stays text; an explainer's legend leaves out empty rows; the explain page's own header style no longer reaches components.
- **Directives no longer switch automatic mode off:** in a Python project, `# karyo:` directives (and `@karyo.node`) now add meaning on top of automatic mode instead of replacing it. Every class and function stays a node, and a directive on a def refines that def's node: its label, category, tags and `calls=` (to an external, say). Without `id=` the node keeps its automatic id, so the curation, tours and recordings still find it. `karyo init` records the choice in a new `karyo/config.json`: `"mode": "auto"` by default, or `--mode directives` for directives only. `karyo refresh` and `karyo record` follow it. **A project already set up with directives changes shape:** it is now read in automatic mode with its directives on top, and refresh and record print a note saying so until `karyo init` records a mode. The SDK's own `python -m karyo scan` keeps its default (automatic mode only when no module has a directive), and `--auto` / `--no-auto` still choose.
- **Constructions are recorded:** the sys.monitoring recorder now sees constructions it missed: a dataclass's generated `__init__`, and classes with no `__init__` of their own when project code builds them. Wires from a composition root no longer read as "not seen running" when the tests ran them (Folio: 4 → 20 of 22). A curation that hides such a type (a record, a reply, an exception) hides it along with its constructions. A bare construction at the root of a flow is not counted among a tour's requests.
- **Tours and splices over type cards:** a tour step naming a type card draws the relationships of its methods in its small diagram and is timed by its methods' spans. A splice op naming a type card (between, before, after, connect, disconnect, remove, replace) applies to what the card stands for on the board, and the board marks the folded wire. Ops that name methods work as before.
- **Import check:** calls made through a typed container (a handler given a `Services` whose attributes are typed with the parts' classes, built by a composition root the handler never imports) are a `wired` note, not a `no-import` warning. So are calls that static analysis resolved.
- **Tours fit the window:** in the theater, `?scene=` and Jarvis a tour lays itself out for the window's shape (code beside the text and diagram in a wide window, stacked in a tall one, the diagram under the code in a low one), fills it, and never draws its header, step rail, code or narration under their readable size or over each other (1000×1300: 57% of the window empty → 0%; chrome no longer at 6.7–9.7 px at 1280–1440 wide).
- **Cleaner structure boards:** a project with no recorded runs (e.g. Swift through markers) draws its wires solid, with one line-key row ("declared in the code") and no "declared, not seen" tag; with recordings nothing changes. Group cards name their inlets and outlets whole with "+n" for the rest, never cutting a count; a wire's count badge keeps clear of cards, group labels and other badges; a wire never dips into the legend; and the groups overview may wrap into two rows to be drawn larger in the window.
- **Swift projects:** `karyo init` recognises a `Package.swift`, `.xcodeproj` or `.xcworkspace` ("swift  Package.swift: 2 targets … / markers  0 yet"), and `karyo refresh` reads `// karyo:` marker comments from its `.swift` files into the model: the same grammar as the Go and Python directives, with the declaration under each marker as the card's symbol, line and code, and warnings for malformed markers, unknown `calls=` targets and ids declared twice. The karyo-adopt skill has Claude write the markers (entry, screens, view models, services, stores, API clients, outside services), then curate and open the view. Markers are kept by hand for now; any other `//` language is one more entry in the scanner's table.
- **Trace boards fit the window:** in the theater, `?scene=` and Jarvis the map's group bands are arranged for the window's shape (as structure boards do), with room for the request column, header and legend at their readable size, so the board fills a wide window and nothing covers a card; requests are named by what they are (what the recording said, else the first declared card they reached, such as an entry point), and their call count no longer clips.
- **Faster Python scan:** `python -m karyo scan` in automatic mode is 2.4 to 5 times faster with byte-identical output (numpy 5.3 → 1.3 s, torch 26 → 5.1 s); a big project's comments are read by two worker processes while the scan parses.
- **Faster big boards:** a structure board no longer re-routes wires whose cards haven't moved, so hovering, zooming and panning a big board costs a fraction of what it did (measured per frame in headless Chrome, a 120-card board fitted to the window: at rest 19.4 → 2.1 ms, zooming 20.0 → 2.6 ms, panning 20.1 → 2.5 ms; 300 cards at rest 210.6 → 5.6 ms; a big relayout glide 11.1 → 5.4 ms at 120 cards). What is drawn is unchanged.
- **Logo:** the Karyo mark (an X chromosome drawn as a graph: four nodes on two chromatids crossing at a centromere node) is the icon of every page and heads the README; the SVGs are in `brand/` (`karyo-mark.svg` follows light and dark, `karyo-icon.svg` is the app tile).
- **`karyo view` ports** now start at 5782 (5782–5799).

- **Splices and groups:** a splice remembers the view it lives in (the group you were inside, Groups or every card, the drill, the selection) and reopening it slides back there; the banner and the Splices list say where it lives, and moving around inside a splice keeps you in it. A splice can propose a new group (the `group` op: nested under a group, attached as an inlet or outlet of a card, with a first card): it shows as a dashed, hatched group card, entering it shows a "No cards yet" placeholder that holds its relationship until the first card takes it over, and Bench has "+ group". Rename and remove work on proposed groups, and combining splices understands them (same-name groups, a removed anchor as a consequence). Jarvis: "splice this", "create a new group called Notifications and attach it to X as an outlet" (it then shows you the new group), "put a Mailer card in it".
- **Group navigation:** a big structure board (28 cards or more) starts as a map of its groups: one card per group with its counts, categories, headline members and what calls in and out, one counted wire per pair of groups (hover: "12 calls from App into Data"). Click a group to slide into its own scene, with its neighbours as inlet and outlet stubs at the edges; a stub slides across, the breadcrumb, `h` or Esc go up a level. Nested curation groups are levels. "Groups / All cards" (or `g`) switches view; force either with the board's `start` option or a curation file's `"start"`. Small boards are unchanged. Jarvis: "go into App", "up a level", "all groups", "show every card"; a card named in another group is found there.

- **Big plates fit the window's shape, and their chrome stays readable:** in the theater and Jarvis, a structure board with many cards wraps its drill rail into columns and picks the layout drawn largest in the window (`pickFit`), so a tall board no longer leaves wide gutters beside it. Chrome (headers, legends, mode lines, toolbars, banners and their buttons, panels, hover cards) is never drawn smaller than its designed size, and the board leaves it room so no card is covered. A new interface size setting (S, M, L) in the ⚙ menu, Jarvis's Settings and `[` / `]` on a plate scales it further.

## 0.2.1

- **Automatic scan:** a local name assigned from itself (`font = font.model_copy()`, or two names that read each other) is treated as unknown instead of looping, so the scan no longer stops with a recursion error on such code.

## 0.2.0

The `karyo` plugin in the `adenine` marketplace: `claude plugin marketplace add adenineio/adenine`, then `claude plugin install karyo@adenine`. Install details: [docs/PACKAGING.md](docs/PACKAGING.md).

- **Engine:** explainer animations built from real HTML elements with a three.js effects layer; every frame is a function of time, so plates can be scrubbed, stepped, screenshotted, linted and exported to video (`scripts/render.ts`).
- **Built-in scenes:** `request-flow`, `code-walkthrough`, `ci-pipeline`, `network-stack` and `layers-stack` (a Stack view), in the gallery (`just dev`).
- **Themes:** adenine (the default) and its colour schemes, plus neutral (light, dark or following the OS). A link or a stored choice that names a theme not on the list opens the default. Built explainer files load no web fonts and need no network.
- **Models from code:** the `karyo.model.json` format (`"karyo": 1`, JSON Schema in `spec/`), Python and Go SDKs that declare, scan and record, and a merge that reconciles declared, extracted and observed structure into warnings. `karyo model scan` reads Python `# karyo:` directives into `.karyo/` and builds the model; `karyo model build` merges fragments; `just stack-history` turns a model file's git history into Stack view slices, following renames and moves.
- **Views of a model:** structure map and flow replay, the structure board (Bench, theater, Splice: sandboxed what-ifs saved as `karyo/splices/*.splice.json`, stacked and combined), trace boards, tours, sequence plates and the Stack view. A board's `lead` option names the tag and wire its example states lead with.
- **Project view:** `karyo view` (or `/karyo:view`) serves `project.html` for any project on a free port in 5781–5799: its models, recorded flows, tours and explainers. Splices and the team layout save into the project; outside a project view, a team layout saves only as a `karyo.layout.json` beside a `karyo.model.json`.
- **Explainers:** JSON specs of components, links and steps, validated, previewed as stills and built into one self-contained HTML file; built-in and custom components (`components/`, `karyo component …`).
- **Kits:** node kinds and plate types from `karyo/kits/<name>/` folders; a kit that runs its own JavaScript does so only in a sealed frame, after the viewer trusts that version.
- **Skills:** `karyo-explain`, `karyo-adopt`, `docket`, `view` and `jarvis`.
- **MCP server:** `karyo` (`plugin:karyo:karyo`) to create, validate, preview and build explainers from Claude Desktop, Cowork or Claude Code.
- **CLI:** `cli/karyo` (`view`, `jarvis`, `stop`, `status`, `model`, `setup`, the explainer, component, kit and docket commands), called by the skills by full path.
- **Docket:** one Markdown sheet per repository of decisions, reviews and things to come back to, shared by every worktree.
- **Jarvis:** voice control of a plate (`karyo jarvis` or `/karyo:jarvis`): local Whisper speech recognition (the official weights, SHA-256 checked, fetched on first use) and a `claude -p` brain. Its page opens `layers-stack` when no scene is given.
- Everything Karyo installs for itself (JS dependencies, Python environments, Whisper weights, caches, logs) lives in the plugin's data dir, never in the project.
- **Adopt Karyo in one sentence:** the `karyo-adopt` skill ("set up Karyo here", "refresh Karyo") runs `karyo init`, the first automatic scan, a proposed curation (`karyo/curation.json`), one recording of the tests, the view, and offers a refresh hook. docs/ADOPT.md.
- **`karyo init`:** detects the project (packages, tests, package manager, CI, justfile or Makefile), shows a plan and asks; writes the launcher `karyo/karyo.sh`, `.gitignore` entries for generated files, `karyo-*` recipes, a dev dependency only for the SDK's code form, and on request a CI workflow and a refresh hook (Claude Code Stop or PostToolUse, or git post-commit), into the project only. Idempotent; `--remove` takes it all out.
- **`karyo refresh`** (re-scan in automatic mode and rebuild; reports unresolved curation entries and drift; `--check` for CI, `--hook` quiet and debounced) and **`karyo record`** (the tests once under sys.monitoring).
